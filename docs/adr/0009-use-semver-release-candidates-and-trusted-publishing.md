# ADR-0009: Use SemVer release candidates and trusted npm publishing

## Status

Accepted

## Context

Codefox UI now has enough reusable surface to be consumed by applications before the public API is considered 1.0-stable. Consumers need a clear distinction between ordinary releases and builds that are still being validated in a real application.

Publishing must be repeatable, must not depend on a maintainer running `npm publish` from a workstation, and should avoid long-lived npm write credentials.

npm supports trusted publishing from GitHub Actions through OIDC. Trusted publishing requires the npm package to exist before the trust relationship can be configured, so the very first package publication needs a one-time bootstrap credential.

## Decision

Use Semantic Versioning for `@codefoxpro/ui`.

Before 1.0, the API may still evolve incompatibly, but version changes remain deliberate and documented. Builds that are not yet ready to be treated as an ordinary release use release-candidate versions:

```text
0.1.0-rc.1
0.1.0-rc.2
0.1.0
0.2.0-rc.1
0.2.0
```

Release-candidate numbering is scoped to the target SemVer version and increases monotonically.

The version is committed in `package.json`. A GitHub Release tag must exactly match it with a leading `v`, for example `v0.1.0-rc.1`.

Publishing is triggered only by publishing a GitHub Release. The release workflow verifies that:

- the tag exactly matches the committed package version
- the tagged commit is contained in `main`
- the version is either `x.y.z` or `x.y.z-rc.n`
- lint, typecheck, tests, package build and Storybook build all succeed before publishing

Release candidates publish to the npm `next` dist-tag. Ordinary releases publish to `latest`.

```text
0.1.0-rc.1 -> next
0.1.0      -> latest
```

Use npm trusted publishing from `.github/workflows/release.yml` with GitHub Actions OIDC. Published packages include npm provenance.

Because npm requires a package to exist before trusted publishing can be configured, the first publication may use a temporary granular npm token stored only as the GitHub Actions secret `NPM_BOOTSTRAP_TOKEN`. Immediately after the first package exists, configure `release.yml` as the npm trusted publisher and delete the bootstrap secret/token. Subsequent publications use OIDC and no persistent npm write credential.

GitHub Releases are the release-note surface. Release notes may be generated by GitHub and edited before the release is published.

## Consequences

- Consumers can opt into candidates with `npm install @codefoxpro/ui@next` while ordinary installs remain on `latest`.
- A release cannot be published from an arbitrary workstation or from a commit outside `main` through the supported process.
- Publishing reruns the complete validation suite, so a failed build or test cannot proceed to npm publication.
- Package versions and Git tags have a one-to-one relationship.
- Preparing a release requires an explicit version change in `package.json` before the GitHub Release is created.
- The first package publication has a documented one-time bootstrap exception because npm cannot establish trusted publishing for a package that does not yet exist.
